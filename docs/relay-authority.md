# WebSocket authority

This is a room and shared-container relay, not a full physics or personal-inventory authority. The connection that claimed a name owns that claim; the relay assigns room IDs, session-resume tokens, and the host socket. Choosable names, positions and UID strings do not confer another connection's rights. Shared worlds can use Survival or Creative; the older `classic` wire edition remains supported for existing clients and is creative-only. Shared containers (chests, furnaces, and storage minecarts) are mutated atomically on the relay via `container:tx`, while personal player bags remain local to each client.

The `beta` edition remains the wire name for the shared game. `room:create` with `terrain: "overworld-v1"` selects the 256-block Overworld generator paired with the 128-block Nether (`"nether-v1"`), retains the exact seed, and requires clients to supply that capability in `rooms:list` and `room:join`. Per-dimension `edits`, `chests`, and `furnaces` are retained independently across Overworld <-> Nether transitions (`room:dimension`). Omit `terrain` for legacy Beta (128 blocks) or Classic (64 blocks with finite horizontal bounds). Short connection drops can reclaim the exact in-room slot and role via `session:resume` before the grace timer expires; leaving or closing does not turn room contents into a singleplayer save.

| Message from client | Who can act and what they may change |
|---|---|
| `ping`, `players:list`, `rooms:list` | Anyone connected. Read only; the room list shows public rooms with space. |
| `player:claim`, `player:release` | Connection may claim an available case-insensitive name or release its own claim. Release leaves its room. |
| `session:resume` | Reconnecting client presenting a valid `{ code, resumeToken }` within the grace window reclaims its previous `clientId`, player name, and host/guest role, receiving a fresh room/container/world snapshot. |
| `room:create` | Named client not in a room becomes its room's host. Edition, Survival/Creative mode, seed, access, optional room password and optional shared visuals are set at creation; reply includes `resumeToken`. |
| `room:join`, `room:leave` | Named client acts for itself; join needs a matching room code, password if set, and a free slot, and returns `resumeToken`. Explicit `room:leave` by host closes its room. |
| `room:close` | Current room's host only. |
| `room:dimension` | Host switches the active room dimension (`overworld` or `nether`), preserving per-dimension edits/containers and pushing the target dimension snapshot to peers. A guest stepping into a portal sends `room:dimension`, which the relay forwards as `portal:travel` for the host to adjudicate. |
| `player:state`, `chat` | Current members act as themselves. Relay stamps the sending identity. Other clients cannot update that identity. |
| `world:snapshot` | Host may publish validated edit batches for the active dimension. Canonical block coordinates identify entries, not an owning player. |
| `world:edit` | Any member may place/remove a valid block within the active dimension's build bounds. Last accepted edit at a coordinate wins; setting air (`0`) at a chest or furnace coordinate spills its stored stacks via `srv:` `item:spawn` and emits `container:remove`. |
| `container:snapshot` | Host may seed initial chest and furnace maps for `overworld` or `nether` when opening or transitioning a saved world. |
| `container:tx` | Any member in the room may execute atomic `click`, `take`, or `insert` operations on a valid `chest`, `furnace`, or `cart` (storage minecart). Relay replies with `container:ack` (including `xpEarned` for furnace output) and broadcasts `container:state` to peers. Relay ticks furnaces across both dimensions every 250 ms. |
| `game:state` | Host publishes shared time and world state under the payload limit. |
| `item:snapshot` | Host replaces the shared drop collection (preserving item `enchants`), including removal by omission. Snapshot IDs must be unique. |
| `item:spawn` | Host can publish valid drops; guests may publish valid drops near their last reported live position. IDs are scoped to the sender and cannot replace live drops. |
| `item:pickup` | Any member with a reported live position within five blocks may request an existing drop. The relay removes it first, grants it only to the requester, and tells peers to remove it. Clients cannot issue the grant. |
| `projectile:update`, `projectile:remove` | A member may create a player projectile (`arrow`, `snowball`, `egg`, `xp_bottle`, deflected `fireball`) or control its own existing projectile; only the host creates mob projectiles (`arrow`, `fireball`, `blaze_bolt`). Relay expiry and sender disconnect remove stale projectiles. |
| `vehicle:update`, `vehicle:remove` | First valid creation sets the owner. Only the owner may update the existing vehicle and its type cannot change. Owner or host may remove it; removing a `storage` minecart spills its `vehicleContainers` contents and emits `container:remove`. |
| `tnt:ignite`, `mob:attack` | Guest can submit bounded requests (including melee/ranged enchantment metadata) for the host to validate and simulate; neither message directly mutates an entity on the relay. |
| `player:damage`, `mob:snapshot` | Host alone may relay bounded damage to a current player or replace the shared mob list (up to 64 active mobs) with valid, unique records. |

Server-only types: `pong`, `error`, `player:claimed`, `player:released`, `player:joined`, `player:left`, `room:joined`, `room:resumed`, `room:left`, `room:closed`, `room:dimension:accepted`, `room:dimension:queued`, `portal:travel`, `world:snapshot:accepted`, `container:snapshot:accepted`, `container:ack`, `container:state`, `container:remove`, `item:remove`, `vehicle:snapshot`, and `projectile:snapshot`. The relay also emits the compatible list, state, update, and removal notifications in the table. Server notifications are not authority a client can claim by reflecting them back.

Only recognized text JSON messages reach handlers. The transport caps messages at 1 MiB; recognized messages other than room creation, world/item snapshot and game state have a 64 KiB cap. Handlers further bound rates, collection sizes and key fields. These checks do not prove reported positions, physics, inventory conservation or host correctness. Rooms and names remain process-local, with at most five rooms and five players per room.
